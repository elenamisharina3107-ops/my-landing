# Шаблон админ-панели для сайтов — концепция

Черновик от 2026-09-01. Автор идеи — Лена (Vireflow). Документ для обсуждения, не финальное ТЗ.

---

## Зафиксированные решения (2026-09-01)

- **Строим своё** — вариант A (собственная панель на FastAPI, Git как хранилище контента).
  Готовые CMS (Decap/Sveltia) не берём. Причина Лены — нужен свой брендированный кабинет
  под все сайты + возможность встроить редактор ИИ-сотрудника. Риск осознан: это разработка
  и поддержка собственного продукта (обновления, безопасность, аптайм на всех клиентах).
- **Кто редактирует:** основной пользователь — **клиент** (владелец сайта). Лена
  редактирует тоже, если сайт у неё на обслуживании. → нужны роли и разграничение доступа
  по сайтам с первой версии, UI с «защитой от дурака».

---

## 1. Суть идеи (как её сформулировала Лена)

> «Я делаю сайты на заказ. Хочу разработать шаблон админ-панели, чтобы при разработке
> сайтов всё это шло быстрее».

Один раз сделать переиспользуемый «движок» админки, который подключается к любому новому
сайту почти без программирования. Каждый заказ тогда сдаётся с готовой панелью управления:
клиент сам меняет тексты, цены, картинки, услуги — а Лена не пишет индивидуальную админку
под каждый проект и не тратит время на мелкие правки после сдачи.

«CMS для редактирования контента» уже заявлена в прайсе Лены как фича пакетов — сейчас под
неё нет типового решения, каждый раз собирается вручную.

## 2. Зачем это нужно (бизнес-цель)

- **Скорость.** Сборка и сдача сайта быстрее → больше заказов за то же время, ниже
  себестоимость каждого.
- **Цена и ценность.** «Сайт + панель управления» продаётся дороже статики. Клиент,
  который сам правит контент, не уходит к конкуренту ради замены одного абзаца.
- **Удержание и допродажи.** Панель — естественная точка входа для пакета сопровождения
  и для пакета «сайт + ИИ-сотрудник» (в той же панели редактируется промпт бота и его
  прайс).
- **Разгрузка Лены.** Рутинные правки после сдачи уходят клиенту, Лена занимается
  разработкой, а не поддержкой текста.

## 3. Что уже есть — прототип (прошлый опыт, не с нуля)

`~/projects/alyona-bot-prod/admin_panel.py` — рабочая одностраничная админка для лендинга
`my-landing`:

- FastAPI, вход по одному паролю, сессии в памяти (8 ч). Отдаётся под
  `https://api.vireflow.ru/admin/`, systemd-сервис `admin_panel.service`, порт 8002.
- Редактирует ~9 полей: 3 цены + 3 «старые» цены, заголовок и подзаголовок героя,
  `system_prompt` бота.
- При сохранении: пишет локальный `content.json` **и** коммитит его в ветку
  `feature/admin-panel` репозитория `my-landing` через GitHub Contents API.
- Сайт на загрузке дёргает `GET /admin/api/public/content` и подменяет значения на странице
  через атрибуты `data-price="landing|site|system"` и `data-text="hero-title|hero-subtitle"`.

### Почему это ещё не «шаблон»

| Ограничение | Следствие |
|---|---|
| Один сайт, один клиент, один общий пароль | Нельзя выдать двум клиентам, нет разграничения |
| Схема полей зашита в HTML дашборда и в Python | Под новый сайт нужно править код панели |
| Путь к файлу контента захардкожен и сейчас битый (`/root/my_bot_new/content.json` не существует) | Панель молча отдаёт значения по умолчанию, правки цен не доходят |
| Нет картинок, списков (услуги, отзывы, FAQ, блоки), нет медиа-загрузки | Реально редактируется только текст и числа |
| Коммит идёт в отдельную ветку, а не в прод-ветку сайта | В статическую сборку контент не попадает — только через живой запрос к API в рантайме |
| Нет истории версий, предпросмотра, отката | Ошибку клиента нечем откатить |
| Сессии в оперативной памяти | Рестарт сервиса разлогинивает всех |

Вывод: прототип доказал схему «правка → коммит в Git → сайт берёт контент», но как
тиражируемый продукт требует переписывания ядра.

## 4. Целевая картина (v1)

**Config-driven панель.** Контент-модель конкретного сайта описывается одним файлом-схемой
(например `content.schema.json`): какие есть поля, их типы (текст, многострочный текст,
число, картинка, список объектов, ссылка, булев флаг), группировка по секциям, подсказки.

Панель читает схему и **сама рисует форму** — под новый сайт не пишется код, только схема
и разметка страницы с «якорями» под поля.

Поток данных остаётся git-ориентированным (как в прототипе, это оказалось удачно):
правка в панели → запись в `content.json` сайта → коммит/PR в репозиторий сайта →
пересборка/деплой. Это даёт бесплатную историю версий и откат через Git.

### Роли

- **Лена (разработчик).** Заводит сайт: схема + подключение репозитория. Видит все сайты.
- **Клиент (владелец сайта).** Логинится, редактирует только свой сайт, только поля из
  схемы. После сдачи — это его основной интерфейс.

## 5. Архитектурные варианты (нужно выбрать до старта)

### A. Развить свой прототип
FastAPI + рендер формы по схеме + запись в Git + мультитенант (список сайтов, свои
доступы). Хостится у Лены, один кабинет на все сайты.
*Плюсы:* полный контроль, единое окно под все проекты, легко впаять редактор промпта
ИИ-сотрудника. *Минусы:* это разработка и поддержка собственного продукта — обновления,
безопасность, аптайм на всех клиентах сразу.

### B. Git-CMS с открытым кодом
**Decap CMS** (бывш. Netlify CMS), **Sveltia CMS**, **Tina**, **Pages CMS**. Это ровно
текущий паттерн Лены (правки → коммит в GitHub), но бесплатно, с готовым UI, загрузкой
медиа, превью и поддержкой сообщества. Контент-модель описывается конфигом — та самая
«схема», что в варианте A пришлось бы писать самим.
*Плюсы:* почти ноль бэкенда, быстрый старт, не нужно поддерживать своё. *Минусы:* UI не
брендированный «под Vireflow», редактор ИИ-промпта — отдельно, авторизация завязана на
GitHub/OAuth-провайдера.

### C. Headless CMS-сервер
**Directus**, **Strapi**, **PocketBase**. БД, REST/GraphQL API, медиатека, роли из коробки.
*Плюсы:* мощно, масштабируется. *Минусы:* на каждом клиенте — сервер и БД, которые надо
хостить и обновлять; тяжело для лендинга на 10 полей; уводит от простой статики.

### Честная рекомендация

Прежде чем строить своё (вариант A), **потратить 1 день на Decap CMS / Sveltia** на одном
реальном сайте. Они делают ~80% задуманного бесплатно и годами поддерживаются. Ранее уже
был вывод не строить собственную мини-платформу при работе в одиночку и нуле продаж
(`~/projects/biznes/noya-ai-analysis.md`) — тот же риск здесь.

Своя панель (A) оправдана, только если критично: (1) единый брендированный кабinет «одно
окно под все сайты клиента», (2) редактор ИИ-сотрудника и контента в том же интерфейсе,
(3) выдача доступа клиенту без заведения его в GitHub. Если это важно — можно взять
гибрид: тонкая своя обёртка + Git как хранилище.

## 6. Объём MVP (первая версия, что бы ни выбрали)

1. Схема контента в одном файле; поддержка типов: строка, текст, число, картинка, список.
2. Автогенерация формы по схеме, разбивка по секциям, подсказки к полям.
3. Логин (пароль или magic-link), сессии в постоянном хранилище.
4. Сохранение: запись `content.json` + коммит в репозиторий сайта.
5. На стороне сайта — типовой сниппет, подставляющий контент по атрибутам (`data-cms="..."`).
6. Инструкция «как подключить новый сайт за N шагов».
7. Один реальный сайт переведён на этот шаблон (боевая проверка).

### За рамками MVP

Загрузка и оптимизация изображений, предпросмотр черновика, история/откат через UI,
несколько пользователей на один сайт, роли и права по секциям, мультиязычность,
аналитика в панели, биллинг клиентов, drag-and-drop блоков.

## 7. Модель поставки и деньги (черновые гипотезы)

- **Включено в сайт.** Панель идёт бонусом к пакету, хостит Лена. Держит клиента и
  оправдывает цену выше статики.
- **Сопровождение от 3 000 ₽/мес.** Хостинг панели + N правок структуры + обучение.
- **«Под ключ, отдаём клиенту».** Клиент получает панель на своём хостинге/аккаунте —
  разовая цена выше, дальше он сам (пересекается с логикой пакетов на Ное из
  `vireflow-bots`).
- Себестоимость подключения нового сайта после готового шаблона — часы, не дни; это и есть
  основная экономия.

## 8. Открытые вопросы к Лене

1. **Build vs. buy:** готова ли потратить день на Decap/Sveltia перед тем как строить своё,
   или принципиально хочешь собственную панель под бренд?
2. **Хостинг:** один кабинет у тебя на сервере под все сайты — или отдельная установка на
   каждый проект?
3. **Кто заходит:** только ты правишь по заявке клиента — или клиент сам? (влияет на
   требования к UI, правам, «защите от дурака»).
4. **Стек сайтов:** сейчас статический HTML. Будущие сайты — тоже статика, или Next/Astro?
   От этого зависит, брать контент в рантайме или на сборке.
5. **Медиа:** нужна ли загрузка картинок в v1, или пока только текст и цены?
6. **ИИ-сотрудник:** редактор его промпта — часть этой панели сразу, или отдельно?
7. **Приоритет:** это ускорение текущих заказов (делаем быстро и грубо) или отдельный
   продукт на продажу (делаем аккуратно)?

## 9. Ближайшие шаги (после ответов на вопросы)

1. Зафиксировать выбор из раздела 5 → отдельное ТЗ / план.
2. Собрать `content.schema.json` для одного реального сайта как эталон.
3. Прототип рендера формы по схеме.
4. Подключить первый сайт, проверить полный цикл «правка → Git → деплой».
5. Написать инструкцию по подключению следующего сайта.
