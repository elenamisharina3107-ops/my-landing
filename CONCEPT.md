# Шаблон админ-панели для сайтов — концепция

Черновик от 2026-09-01. Автор идеи — Лена (Vireflow). Документ для обсуждения, не финальное ТЗ.

---

## Зафиксированные решения (2026-09-01)

- **Строим своё.** Собственная панель на FastAPI. Готовые CMS (Decap/Sveltia) не берём —
  Лене нужен свой брендированный продукт под пакеты Vireflow и задел под редактор
  ИИ-сотрудника. Риск осознан: это разработка и поддержка собственного продукта.
- **Главный принцип — независимость клиента после сдачи.** Клиент получает сайт вместе с
  панелью в собственность и правит его сам по своему логину/паролю. Он **не должен зависеть
  от серверов, репозиториев или аккаунтов Лены**. У Лены остаётся только доступ (второй
  аккаунт), а не контроль над инфраструктурой.
- **Кто редактирует:** основной пользователь — **клиент**. Лена заходит тоже, если сайт у
  неё на обслуживании. → нужны минимум две роли и «защита от дурака» в UI с первой версии.
- **Медиа:** загрузка картинок (фото, логотип) — **в первой версии**.
- **Редактор промпта ИИ-сотрудника:** отдельный модуль, **позже**. Ядро проектируем так,
  чтобы его можно было подключить плагином.
- **Стек сайтов:** пока не определён. Проектируем под статические HTML-сайты (как сейчас),
  с заделом на генератор (Astro/11ty) позже.

## 1. Суть идеи (как её сформулировала Лена)

> «Я делаю сайты на заказ. Хочу разработать шаблон админ-панели, чтобы при разработке
> сайтов всё это шло быстрее».

Один раз сделать переиспользуемый «движок» админки, который ставится на любой новый сайт
почти без программирования. Каждый заказ тогда сдаётся с готовой панелью управления:
клиент сам меняет тексты, цены, картинки, услуги — а Лена не пишет индивидуальную админку
под каждый проект и не тратит время на мелкие правки после сдачи.

«CMS для редактирования контента» уже заявлена в прайсе Лены как фича пакетов — сейчас под
неё нет типового решения, каждый раз собирается вручную.

## 2. Главное ограничение: независимость клиента

Это определяет всю архитектуру. Клиент после сдачи:

- владеет сайтом и панелью, они стоят на **его** хостинге / его домене;
- входит по своим логину и паролю, может сменить пароль, может завести своих людей;
- может уйти от Лены и не потерять ни сайт, ни возможность его редактировать;
- не платит Лене за сам факт работы панели (только за сопровождение, если сам захочет).

Из этого следует: **никакого общего SaaS-кабинета на сервере Лены**, никакого хранения
контента в её GitHub. Каждый сайт — самодостаточный комплект, который разворачивается
отдельно. Лена держит у себя только «эталон» (шаблон-репозиторий), из которого клонирует
новый проект.

## 3. Зачем это нужно (бизнес-цель)

- **Скорость.** Сборка и сдача сайта быстрее → больше заказов за то же время, ниже
  себестоимость каждого. После готового шаблона подключение нового сайта — часы, не дни.
- **Цена и ценность.** «Сайт + панель управления в собственность» продаётся заметно дороже
  статики и звучит солиднее в объявлении.
- **Аргумент независимости — сам по себе продающий.** «Вы получаете сайт и панель в
  собственность, не привязаны к разработчику» — сильное отличие от студий, которые сажают
  клиента на свою подписку.
- **Удержание и допродажи.** Панель — естественная точка входа для пакета сопровождения и
  для пакета «сайт + ИИ-сотрудник».
- **Разгрузка Лены.** Рутинные правки после сдачи уходят клиенту.

## 4. Что уже есть — прототип (прошлый опыт, не с нуля)

`~/projects/alyona-bot-prod/admin_panel.py` — рабочая одностраничная админка для лендинга
`my-landing`:

- FastAPI, вход по одному паролю, сессии в памяти (8 ч). Отдаётся под
  `https://api.vireflow.ru/admin/`, systemd-сервис `admin_panel.service`, порт 8002.
- Редактирует ~9 полей: 3 цены + 3 «старые» цены, заголовок и подзаголовок героя,
  `system_prompt` бота.
- При сохранении: пишет локальный `content.json` **и** коммитит его в ветку
  `feature/admin-panel` репозитория `my-landing` через GitHub Contents API.
- Сайт на загрузке дёргает `GET /admin/api/public/content` и подменяет значения на странице
  через атрибуты `data-price="..."` и `data-text="..."`.

### Что из прототипа берём

- Идея «панель → сохранение → сайт подхватывает контент» рабочая.
- Рендер простой формы, вход по паролю, отдача публичного JSON для сайта.

### Что переделываем

| Ограничение прототипа | Как надо |
|---|---|
| Один сайт, один общий пароль, схема полей зашита в код | Схема-конфиг под каждый сайт, форма рисуется автоматически |
| Хостинг и GitHub — Ленины | Самодостаточный комплект на хостинге клиента |
| Путь к контенту захардкожен и сейчас битый (`/root/my_bot_new/...`) | Контент в локальном хранилище рядом с приложением |
| Нет картинок, списков, медиа-загрузки | Загрузка изображений + списки (услуги, FAQ, отзывы) с v1 |
| Нет истории версий и отката | Снимок при каждом сохранении + кнопка «откатить» |
| Сессии в памяти, слетают при рестарте | Сессии в постоянном хранилище |
| Две роли не разделены | Роли «владелец» и «редактор», смена пароля |

## 5. Целевая архитектура (v1)

**Самодостаточное приложение на каждый сайт.** Один небольшой сервис (FastAPI), который:

1. отдаёт публичный сайт (статические файлы шаблона + подстановка контента);
2. отдаёт админ-панель под `/admin`;
3. хранит контент в локальной БД (SQLite) и медиа в локальной папке — **рядом с собой**,
   без внешних зависимостей;
4. ведёт историю версий контента (снимок при каждом сохранении, откат на любой прошлый).

Разворачивается как один контейнер (Docker) или один каталог + сервис на хостинге клиента.
Клиенту отдаётся один адрес и доступы. Ничего из инфраструктуры Лены в проде клиента нет.

**Контент-модель — конфиг под сайт.** Файл-схема (`content.schema.json`) описывает поля
сайта: тип (строка, многострочный текст, число/цена, изображение, ссылка, флаг, список
объектов), секцию, подпись и подсказку. Панель читает схему и **сама строит форму** — под
новый сайт кода не пишем, только схему и «якоря» в разметке (`data-cms="hero.title"`).

**Как сайт получает контент** (выбор отложен до определения стека сайтов):
- статические сайты сейчас — подстановка в рантайме JS-запросом к своему же бэкенду
  (как в прототипе, но со своего сервера, не с api.vireflow.ru);
- позже, если появится генератор, — та же схема, но подстановка на сборке.

**Роли:** «владелец» (клиент — всё, включая пользователей и смену пароля) и «редактор»
(правит контент). Лена получает аккаунт «редактор» или «владелец» по договорённости.

## 6. Объём MVP

1. Формат схемы контента + примеры для одного реального сайта.
2. Автогенерация формы по схеме: секции, подписи, подсказки, валидация.
3. Типы полей: строка, текст, число, **изображение (загрузка)**, ссылка, флаг, список.
4. Хранилище: SQLite + папка медиа; история версий с откатом.
5. Вход по логину/паролю, смена пароля, постоянные сессии, две роли.
6. Публичная отдача контента + сниппет подстановки на сайте (`data-cms`).
7. Упаковка: Docker-образ / скрипт установки; README «поднять новый сайт за N шагов».
8. Один реальный сайт (кандидат — `my-landing` или первый клиентский) переведён на шаблон
   и проверен целиком: правка → сохранение → сайт обновился → откат работает.

## 7. За рамками MVP

Оптимизация и ресайз картинок, предпросмотр черновика до публикации, много языков,
права по отдельным секциям, аналитика в панели, биллинг, drag-and-drop блоков,
редактор промпта ИИ-сотрудника (отдельный модуль), синхронизация с внешним Git-репо.

## 8. Модель поставки и деньги (черновые гипотезы)

- **Панель включена в пакет сайта**, отдаётся в собственность клиента вместе с сайтом.
  Обосновывает цену выше статики, звучит в объявлении как «сайт + панель, всё ваше».
- **Сопровождение от 3 000 ₽/мес** (по желанию клиента): хостинг у Лены, N правок
  структуры/схемы в месяц, обучение, обновления панели.
- **Разовая настройка на хостинге клиента** — если клиент хочет полностью у себя: цена
  выше, дальше он сам.
- Экономия Лены — в себестоимости: после готового шаблона новый сайт с панелью собирается
  за часы.

## 9. Открытые вопросы

1. **Хостинг у клиента.** Клиенты Лены — не технари. Кто ставит приложение на их хостинг:
   Лена при сдаче (и передаёт доступы), или нужен «установщик в один клик»? Какой хостинг
   у типичного клиента вообще есть — VPS, шаред, ничего?
2. **Стек сайтов.** Нужно определиться (статика vs генератор) до проектирования подстановки
   контента. Пока проектируем под статику.
3. **Домен и почта для входа.** Панель на поддомене клиента (`admin.сайт.ру`)? Вход по
   email — чьему?
4. **Что именно редактируемо** на типовом сайте Лены — собрать список полей с реального
   лендинга как эталонную схему.
5. **Приоритет:** быстро закрыть текущие заказы (минимально) или сразу делать аккуратный
   продукт на поток?
