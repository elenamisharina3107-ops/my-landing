# Робот сборки и деплоя (`.github/workflows/deploy.yml`)

При каждом push в `main`: `npm ci` → `npm run check:config` → `npm run build`
→ FTP-загрузка папки `_site/` на Beget. Занимает около минуты.

`_site/` содержит и сам сайт, и статику панели Sveltia (`_site/admin/`,
скопированную как есть, см. `.eleventy.js`). Node-приложение `panel/`
(`/admin/_panel/*` — наш вход, история, экспорт) в эту сборку **не входит**
и деплоится отдельно — см. `scripts/beget-setup.md` (Задача 3.2).

## Секреты репозитория (Settings → Secrets and variables → Actions)

| Секрет | Что туда положить |
| --- | --- |
| `BEGET_FTP_HOST` | Адрес FTP-сервера Beget (из панели Beget → FTP) |
| `BEGET_FTP_USER` | Логин FTP-аккаунта |
| `BEGET_FTP_PASSWORD` | Пароль FTP-аккаунта |
| `BEGET_FTP_PATH` | Путь на сервере до корня сайта, например `/сайт.ру/public_html/` (со слэшем на конце) |

Заводятся один раз при подключении нового сайта (чек-лист — `scripts/new-site.md`,
Этап 5).

## Важно

- Путь в `BEGET_FTP_PATH` должен указывать на корень **сайта**, а не на всю
  учётную запись Beget — иначе робот перезапишет что-то соседнее.
- Экшен (`SamKirkland/FTP-Deploy-Action`) синхронизирует папку целиком: то,
  что удалено из `_site/` при следующей сборке, удалится и на сервере.
  Файлы `panel/` в `_site/` не попадают в принципе — их эта синхронизация
  не касается.
- Первый прогон робота лучше проверить на тестовом FTP-доступе, прежде чем
  указывать боевой (см. проверку в Задаче 3.2).
