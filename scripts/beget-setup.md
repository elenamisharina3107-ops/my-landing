# Настройка Beget для нового сайта

Разовый чек-лист на аккаунт клиента (или общий, если хостинг остаётся на
обслуживании у Лены — см. решение 7 в плане). Выполняет Лена, агент может
подсказывать команды и проверять результат по URL.

## 1. Тариф и домен

1. Тариф **Blog** (~420 ₽/мес, до 5 сайтов) — этого достаточно для одного
   лендинга с панелью.
2. Привязать домен клиента (или завести поддомен, если домена ещё нет).
3. Включить бесплатный SSL (Let's Encrypt) в панели Beget для домена —
   без него браузер клиента будет ругаться на сайт и не даст войти в панель
   (cookie сессии ставится с `secure` в проде, см. `panel/session.js`).

## 2. Поддержка Node.js — проверить в первую очередь

**Находка (3 сентября 2026, тариф Blog, реальный аккаунт):** отдельного
раздела «Node.js» в панели Beget **нет** — ни на общей странице хостинга,
ни в настройках конкретного сайта (там только версия PHP). Node.js
устанавливается вручную по SSH, а обслуживается сайтом через Apache
`mod_passenger`, а не через отдельный «менеджер приложений». Официальная
инструкция Beget: https://beget.com/ru/kb/how-to/web-apps/node-js.

Реальные шаги (проверено вживую):

1. Подключиться по SSH к `ЛОГИН@сайт.beget.tech` (или домену), затем **зайти
   во внутреннее docker-окружение** — снаружи у обычной SSH-сессии нет
   исходящего интернета для скачивания Node: `ssh localhost -p 222` (тот же
   пароль). Проверить версию Ubuntu: `cat /etc/os-release` (на Blog —
   22.04 → доступны версии Node вплоть до последних, ставили 20.20.2).
2. Внутри docker-окружения:
   ```
   mkdir -p ~/.local && cd ~/.local
   curl -sS -o node.tar.xz https://nodejs.org/download/release/v20.20.2/node-v20.20.2-linux-x64.tar.xz
   tar xf node.tar.xz --strip 1 && rm node.tar.xz
   ~/.local/bin/node -v   # v20.20.2
   ```
   (Официальный пример использует `wget` — у нас зависал без видимой причины,
   `curl` с тем же URL отработал мгновенно; возможно, совпадение конкретной
   сессии, не факт про сам wget.)
3. `~/.local/bin/node` и `~/.local/bin/npm` работают и **снаружи** docker-
   окружения (та же файловая система) — `npm install` внутри docker (там есть
   интернет), запуск — уже не важно, где.

## 3. Структура папок на сервере

```
/сайт.ру/public_html/          ← корень сайта, сюда FTP-робот кладёт _site/
/сайт.ру/public_html/admin/    ← статика Sveltia (часть _site/, тот же деплой)
/сайт.ру/panel/                ← Node-приложение panel/ — ВНЕ public_html
/сайт.ру/panel/store/          ← config.json, users.json — вне веб-корня и вне git
```

`panel/store/*.json` не должны быть доступны по прямой ссылке ни при каких
обстоятельствах — поэтому вся папка `panel/` кладётся выше `public_html`,
а наружу торчит только то, что настроено в шаге 5 (`/admin/_panel/*`).

## 4. Завести Node-приложение

Готового «менеджера приложений» нет (см. шаг 2) — приложение поднимается
вручную через Passenger, без отдельной панели настроек.

1. Загрузить содержимое `panel/` (код, `package.json`, **без**
   `node_modules` и без `store/config.json`/`users.json`) на сервер, ВНЕ
   `public_html` — например `~/panel` (SCP/SFTP).
2. Поставить зависимости — **тоже внутри docker-окружения** (шаг 2), там
   есть интернет: `cd ~/panel && ~/.local/bin/npm install --omit=dev`.
3. Создать `panel/store/config.json` и `users.json` прямо на сервере (не
   через git) — репозиторий, токен бота, `sessionSecret` (случайная строка
   от 32 символов), ссылка на поддержку. `chmod 600` на оба файла.
4. Создать первого пользователя-владельца:
   `~/.local/bin/node -e "import('./users.js').then(u => u.createUser('./store/users.json', {email: 'ПОЧТА_КЛИЕНТА', role: 'owner'}).then(r => console.log(r.tempPassword)))"`
   — временный пароль вывести на экран и передать клиенту отдельно (не в
   письме вместе с логином).

## 5. Прокинуть `/admin/_panel/` на Node-приложение (Apache mod_passenger)

Никакого отдельного экрана «маршрут для Node.js» в панели нет — это делает
`.htaccess` через Apache-модуль Passenger, который на Beget уже стоит и
включён. Создать **пустую** папку `public_html/admin/_panel/` (сам код
приложения там не лежит — только этот файл, он лишь помечает URL-префикс)
и положить в неё `.htaccess`:

```
PassengerEnabled on
PassengerAppType node
PassengerStartupFile serve.js
PassengerAppRoot /ПОЛНЫЙ/ПУТЬ/ДО/panel
PassengerNodejs /ПОЛНЫЙ/ПУТЬ/ДО/.local/bin/node
```

(пути — абсолютные, узнать через `realpath ~/panel` и
`realpath ~/.local/bin/node`; `serve.js`, не `server.js` — см. находку
про точку входа ниже). Всё остальное в `public_html` (включая `/admin/`
со статикой Sveltia) Passenger не трогает — обслуживается обычным Apache
как раньше.

**Решённая проблема 1 — права на папку (4 сентября 2026):** Beget запускает
каждый сайт от отдельного изолированного пользователя (в тексте ошибки
Passenger — что-то вроде `САЙТ__хэш`), и по умолчанию он не видит папку
`panel/`, даже если она принадлежит тому же аккаунту. Ошибка: _"must be
able to access its application root directory... wrong permissions"_.
Диалог в файловом менеджере («Инструменты» → «Настроить общий доступ к
директории» → «Чтение и запись» + «Включая вложенные папки» → «Открыть
доступ») **на глаз выглядел применённым, но реально не давал доступа ни
к чему внутри папки** (`getfacl` показывал `other::r-x` у самой `panel/`,
но `other::---` у любого файла или подпапки внутри, включая файлы прямо
в корне) — это подтверждённый баг/ограничение именно для уже
существующих файлов на их стороне, не ошибка настройки с нашей стороны.
Прямой `setfacl` по SSH запрещён системой даже владельцу файла — фикс
может сделать только сама техподдержка Beget на своей стороне (тикет,
конкретный домен + вывод `getfacl` до/после — ускоряет). После их
вмешательства доступ действительно появился.

**Решённая проблема 2 — точка входа не запускалась под Passenger (4
сентября 2026):** даже после починки прав `/health` не отвечал — Passenger
запускал файл, но наш код никогда не начинал слушать порт. Причина: старый
`server.js` запускал сервер только под условием
`if (import.meta.url === \`file://${process.argv[1]}\`)` (чтобы не поднимать
сервер, когда файл просто импортирует тест) — **под Apache mod_passenger
это условие никогда не выполняется** (Passenger подключает файл не так,
как обычный `node server.js`), и сервер молча не стартовал, без единой
ошибки в логах. Решение — не пытаться угадывать, как именно нас запустили,
а развести на два файла: `server.js` (только `createApp`, без побочных
эффектов — безопасно импортировать откуда угодно, в т.ч. из тестов) и
`serve.js` (новый, единственная задача — безусловно поднять сервер;
именно на него теперь указывает и `PassengerStartupFile`, и `npm start`).
Заодно `serve.js` слушает явно `127.0.0.1`, а не все интерфейсы — так
проверено вживую, что Apache находит приложение.

## 6. Проверка (Задача 3.2 — «зелёная проверка»)

- `https://сайт.ру/admin/_panel/health` → `200 {"status":"ok","repo":"..."}`
  — **пройдено вживую 4 сентября 2026** на `elenamfv.beget.tech`.
- `https://сайт.ру/admin/` → отдаёт панель Sveltia (статика) — ещё не
  проверено, статика сайта пока не выложена в `public_html`.
- `https://сайт.ру/` → отдаёт собранный сайт-заглушку — тоже ещё не
  проверено.

Если что-то не совпало — сверить шаг 5 (маршрутизация, права на файлы,
имя файла в `PassengerStartupFile`) и переменные окружения Node-приложения.
Диагностика: временно добавить в `.htaccess` строку
`PassengerFriendlyErrorPages on` — тогда страница ошибки Passenger покажет
точную причину (обязательно убрать после того, как разобрались — не
оставлять на боевом сайте).

## 7. Подключить робота (после того как 1–6 пройдены)

Прописать секреты `BEGET_FTP_HOST/USER/PASSWORD/PATH` в GitHub (см.
`scripts/deploy-notes.md`) — `BEGET_FTP_PATH` указывает на `public_html/`
из шага 3, не на всю учётную запись.
