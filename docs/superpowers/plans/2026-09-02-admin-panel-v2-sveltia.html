Для Лены

Простым языком

Из чего собран один сайт с панелью:

  • сайт — обычные готовые файлы, лежат на хостинге Beget (оплата рублями, всё в одной компании: хостинг + домен + почта + бесплатный SSL);
  • тексты и картинки — лежат отдельными файлами в «главной папке» проекта на GitHub (бесплатный склад). Это и есть «контент в собственности» — обычные файлы, которые принадлежат клиенту;
  • панель по адресу сайт.ру/admin — готовый бесплатный редактор Sveltia CMS с твоим логотипом. Мы его не программируем, только настраиваем;
  • «робот» (GitHub Actions, бесплатно) — после нажатия «Опубликовать» собирает сайт заново и кладёт на Beget. Занимает ~1 минуту;
  • маленький вход — наша страница логина по email и паролю, чтобы клиент не видел GitHub. Это единственный кусок, который мы пишем сами, и он небольшой.

Что делаешь ты для нового сайта: копируешь заготовку → заполняешь список полей (что клиент сможет менять) → собираешь внешний вид со мной → заводишь клиенту склад на GitHub и хостинг на Beget по чек-листу → создаёшь логин, отдаёшь доступ.

Что делает клиент: заходит на сайт.ру/admin, вводит email и пароль (GitHub не видит), правит текст / цену / картинку / список, жмёт «Опубликовать», через минуту сайт обновился. Ошибся → «История» → «Вернуть эту версию».

Что мы получаем бесплатно (в прошлом плане это надо было программировать и охранять): история всех версий, откат, черновик→публикация, загрузка картинок.

Честные минусы
  1. После «Опубликовать» сайт обновляется через ~1 минуту, не мгновенно.
  2. «Маскировка GitHub» работает на 90%. Технически ключ доступа к складу оказывается в браузере клиента — очень любопытный клиент теоретически может его достать и зайти в свой же склад напрямую. Вреда другим сайтам это не наносит (ключ только от его склада).
  3. При настройке нового сайта на один шаг больше, чем на Vercel (подключить «робота»), — но это разовый рецепт по чек-листу.

Технологии: Eleventy (11ty) v3 — генератор статики; Sveltia CMS — панель (формат конфига совместим с Decap CMS); Node.js 20 — маленькое приложение входа / истории на Beget; GitHub + GitHub Actions — склад и «робот»; @11ty/eleventy-img — сжатие картинок при сборке; Playwright — сквозной e2e; Vitest — юнит-тесты Node-приложения.

Зафиксировано

Принятые решения

Менять, если неверно.

  1. Язык приложения входа — Node.js, не PHP: в песочнице есть Node (можно разрабатывать и тестировать локально), Beget поддерживает Node на виртуальном хостинге. Подтвердить поддержку при заведении аккаунта (Задача 3.2).
  2. Склад — GitHub (не GitLab): туда же встроен бесплатный «робот». Запасной вариант — GitLab, если доступ к GitHub из РФ станет проблемой.
  3. Репозиторий заводится на аккаунт клиента — независимость с первого дня. Отдельный «бот»-аккаунт Лены добавляется соавтором: от него берётся токен для панели и через него Лена работает как editor.
  4. Токен для панели — fine-grained PAT бота, доступ только к одному репозиторию (contents + pull requests). Срок 1 год, продление по напоминанию. Ужесточение (GitHub App, часовые токены) — после пилота.
  5. Черновик→публикация — editorial workflow Sveltia (сохранение уходит в отдельную ветку, «Опубликовать» вливает в основную). Проверить связку с нашим входом рано — Задача 2.4.
  6. Предпросмотр в v1 — панель предпросмотра внутри Sveltia. Отдельный сайт-предпросмотр на поддомене — Этап 5.
  7. Хостинг — по аккаунту Beget на клиента (тариф Blog, 420 ₽/мес, до 5 сайтов). Если клиент отдаёт хостинг на обслуживание — можно держать несколько на одном тарифе, это вопрос пакета поддержки, не архитектуры.
  8. Сжатие картинок — при сборке (eleventy-img): клиент грузит оригинал, робот делает webp и нужные размеры.
Осознанно

Принятые риски

Не чиним в v1
  • Токен в браузере клиента (см. решение 4): ограничен одним репозиторием.
  • Задержка ~1 мин между «Опубликовать» и обновлением сайта (сборка роботом).
  • editorial workflow Sveltia исторически капризен — проверяется отдельной ранней задачей (2.4). Запасной план — одна ветка draft + кнопка «Опубликовать» в /admin/_panel/, вливающая её в main.
  • Счётчик символов в Sveltia из коробки не на всех полях — если критично для заголовков, добавляем свой мини-виджет позже.
  • Переименование поля после запуска: тексты — обычные файлы в git, поэтому переименование = замена ключа в JSON + конфиге + шаблоне одним коммитом, история остаётся читаемой. Инструкция — Задача 5.4. На файлах эта проблема много легче, чем была бы на базе данных.
Правила

Глобальные ограничения

  • Node.js 20, пакетный менеджер npm.
  • Всё, что видит клиент, — на русском: наш вход, письма, кнопки. Интерфейс Sveltia русифицируется её локализацией (проверить полноту — Задача 1.2).
  • Машинное имя поля клиенту не показывается — только label и hint (в Sveltia так по умолчанию).
  • Порядок полей в панели = порядок в admin/config.yml.
  • Секреты (users.json, токен бота, FTP-доступы) — вне веб-корня и вне git. В репозитории — только *.example образцы.
  • Коммит после каждой задачи с зелёной проверкой, формат: feat: / test: / chore: / docs:.
  • Ветка: agent/admin-panel-v2, от master. Каркас Next.js из ветки agent/admin-panel-mvp не используется.
Тестовая стратегия · учли прошлый провал

В плане v1 тесты упирались в отсутствующую базу данных. Здесь:

  • Eleventy-сайт — тестируется локально целиком (build + serve).
  • Sveltia — локально через local backend, без GitHub.
  • Node-приложение — Vitest, GitHub API мокается; один прогон против реального тест-репозитория при наличии токена.
  • Робот-деплой — локально проверяется только сборка; FTP-шаг — «сухой» прогон при заведённом Beget (Задача 3.2).
  • Сквозной e2e — на этапе пилота (Задача 6.1).

Сжатие картинок при сборке

Файлы
.eleventy.js, src/_includes/image.njk
Что делает
Любая картинка из контента при сборке превращается в webp + 2–3 размера; в HTML — <picture> с srcset. Оригинал в src/uploads/ остаётся.
Шаги
  1. npm i -D @11ty/eleventy-img.
  2. Async-shortcode image (src, alt, sizes) → webp + jpeg fallback, ширины 640 / 1280 / 2000.
  3. Секции используют shortcode вместо голого <img>.
Проверка
Тестовый JPEG 3000px в uploads, ссылка из hero.json, npm run build → в _site/img/ webp-файлы ≤2000px; страница показывает картинку.
